# Doctor Skill

## 目的
`doctor` 是 Dum-E 的问题诊断与修复流程技能，用于把故障处理标准化为 Harness Engineering 闭环：
1. 诊断
2. 可观测证据采集
3. 复现
4. 修复
5. 验证
6. 案例沉淀与归档

## 触发条件
出现以下任一情况必须启用本技能：
- 线上或本地故障（报错、超时、空转、错误结果、性能退化）
- 无法稳定复现的偶发问题
- 已修复但缺少可追溯证据链
- 新问题疑似与历史问题相关

## 执行约束（强制）
- 禁止向用户提问，不允许以”等用户确认/等用户补充信息”作为诊断停机条件。
- 诊断与修复必须自主推进到”线上依赖验证通过”为止，不能停在本地编译或单测通过。
- 只要存在任一功能性异常，或可观测日志/事件中出现 `error`（含 `*_error` 事件），必须继续循环修复，禁止结束。
- 若遇到环境阻塞（网络、权限、依赖、配置），先修复环境与 harness 能力，再继续主问题诊断。
- 线上验证未通过时，case 状态不得标记为 `solved` 或 `archived`。
- 最终验收必须由独立 subagent 执行，主 agent 不得自证通过。
- 独立 subagent 必须读取 case 文档并按复现步骤重新执行线上验证。
- 独立 subagent 的日志扫描结果中若出现 `error` 文本或功能异常，判定为失败，必须继续诊断循环。
- 仅当独立 subagent 返回明确通过结论（含命令、日志证据、线上功能正常）才允许结束。
- MiniMax Anthropic 兼容接口基地址使用官方文档口径：`https://api.minimaxi.com/anthropic`。

## 修复质量红线（最高优先级）

**所有修复方案必须满足以下条件，禁止任何形式的降级式修复：**

### 绝对禁止
- 禁止将流式响应降级为阻塞/非流式响应
- 禁止禁用原本正常工作的功能来规避问题
- 禁止以牺牲核心功能为代价换取”能用就行”
- 禁止用更慢的方案替换更快的方案
- 禁止用更低可靠性的方案替换更高可靠性的方案
- 禁止移除已有的可观测能力（日志、事件、tracing）
- 禁止绕过错误处理或隐藏错误信息

### 用户体验与满意度评估（修复前必须自问）

每提出一个修复方案，必须明确回答以下问题，并记录在 case 文档中：

1. **用户体验**：此修复是否让用户感知到功能变慢、变卡、响应变短、交互变繁琐？
2. **满意度**：此修复是否让用户觉得”还不如出问题前”？
3. **性能**：此修复是否导致 agent 单步延迟上升、吞吐量下降、资源占用增加？
4. **任务完成率/准确率**：此修复是否降低了 agent 成功完成任务的概率？
5. **异常定位难度**：此修复是否让未来的 bug 更难追查？

如果任意问题回答”是”或”不确定”，**必须先找到不降级用户体验的替代方案**，才能实施修复。

### 验证 Agent 验收维度

独立验证 subagent 必须对以下每一项做出明确判断（PASS / FAIL / 需要改进），不能只检查”有没有 error”：

1. **功能完整性**：修复后功能与修复前一致，用户无感知差异
2. **性能表现**：响应时间、吞吐量、资源占用无退化
3. **可靠性**：错误处理、边界情况、重试逻辑保持健壮
4. **可观测性**：日志、事件、trace 仍然完整，异常仍可追踪
5. **回归影响**：相关模块和调用链无隐性破坏

### 验证不通过的处置

验证 Agent 返回 FAIL 时，必须同时输出：
- **具体问题**：哪一项维度失败，失败的表现是什么
- **改进建议**：如何调整修复方案使其通过该项
- **禁止事项**：本次验证中发现的”不应该做的事”，防止修复走回头路

主 agent 收到 FAIL 结论后，必须按照改进建议调整方案，重新进入修复-验证循环。

## 强制流程（不可跳步）
1. 问题拆解与初步假设
2. 先查 case 库：
   - 在 `cases/INDEX.md` 与 `cases/*` 中按错误签名、组件、时间范围检索
   - 命中历史 case 时，记录“沿用/不沿用”的理由
3. 采集可观测证据：
   - 必须收集日志、trace、事件、关键配置、请求上下文
   - 若证据不足，优先补齐可观测能力（属于 harness 缺口）
4. 构造最小复现路径：
   - 形成可重复执行的步骤、输入、期望/实际结果
5. 根因分析 + 修复方案：
   - 明确根因链，不接受“猜测式修复”
6. 修复后验证：
   - 同一路径复现验证 + 回归验证 + 线上依赖验证（真实请求链路）
   - 验证窗口内日志/trace 不得出现 `error` 事件；出现则回到步骤 3
   - 启动独立 subagent 执行“二次复现 + 线上验证 + 日志扫描”，其结论必须为 PASS
7. 案例沉淀：
   - 完整记录从发现到修复结束全过程
   - 状态流转：`active -> solved -> archived`

## 可观测性红线
- 如果无法定位问题且无足够观测记录，不得直接给结论“网络问题/偶发问题”。
- 必须先补 observability（事件、错误分类、request id、耗时、重试轨迹等）再继续分析。
- 允许引入“Arthas 类”动态观测方案（按项目技术栈选择），但必须落地为可复用的调试手段。

## Case 管理规则
- 每个问题都要有独立 case 文档，哪怕症状相同但根因不同。
- 新 case 必须基于 `cases/CASE_TEMPLATE.md` 创建。
- 如果引用了其他 case，必须双向维护：
  - 在当前 case 的 `References` 中加被引用项
  - 在被引用 case 的 `Referenced By` 中回填当前 case
- 修复完成后更新 `cases/INDEX.md`。

## 最终完成标准（Definition of Done）
- 根因明确
- 修复方案经过"用户体验/满意度/性能/完成率/可诊断性"自问自答，无降级风险
- 修复方案明确记录了"绝对禁止"检查结果
- 修复合入
- 可复现路径验证通过
- 回归验证通过
- 线上依赖验证通过（真实端到端链路）
- 验证 Agent 五维度验收全部 PASS
- 最终验证窗口无 `error` 文本或 `*_error` 事件
- case 文档完整（含修复质量评估、禁止事项）
- case 已进入正确状态目录（通常先 `solved`，稳定后 `archived`）
